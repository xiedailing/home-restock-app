# 通知 V2：發送當下驗證（已依最新決定實作）

本文件取代先前「事件當下接收者快照」的提案；不採用逐接收者專屬事件內容。

## 規則

- 第一筆事件起固定 60 秒；後續操作不延長截止時間。
- 發送時透過 Items Store 查詢目前有效空間成員，排除操作者、去除重複 ID；不使用待發送批次的舊 `recipientIds` 決定投遞。
- 新加入成員可收到發送當下仍有效的事件；已退出者不收到。無有效接收者或無法取得成員名單時不建立正式通知。
- 已發送通知的接收者、內容、seen/read 保留，不隨後續成員變動重算。
- 不新增個人認購提醒類型；「該補貨了」沿用既有即時提醒條件與成員來源。

## 事件有效性

- 認領／接手：用品仍屬於原共享空間、仍在購買清單、尚未完成，認購者仍是事件操作者，且事件 `operationId` 與用品 `shoppingClaimOperationId` 相同。
- 認購者變更時產生新的操作識別；取消時也更新識別以阻擋過期 Undo，重新認購不沿用舊識別。取消 Undo 僅在既有安全復原規則允許時還原原識別及未截止的原批次，不延長時間。
- 已補貨：用品與空間仍有效，且事件對應的補貨紀錄 ID 仍存在。Undo 或刪除紀錄取消事件；用品已完成補貨本身並不使「已補貨」通知失效。保留原有到期前的補貨 Undo 清理。
- 部分事件失效只發送剩餘有效事件，文案、用品清單與數量一併重建；全失效不發送。

## 持久化與舊資料

- 操作來源先保存，再建立待發送通知；通知入列的來源保存失敗由既有通知錯誤邊界記錄。取消認領及 Undo 則必須先保存來源狀態；來源寫入失敗不套用該操作，通知寫入失敗不撤銷已保存的來源結果。
- 發送結果、移除的待發送批次及診斷在同一通知 Key 保存成功後，才更新記憶體。失敗保留原批次，後續處理重新查詢成員，不重複建立同批通知。
- 舊待發送已補貨事件可用穩定補貨紀錄 ID 驗證；舊認領／接手若缺少可核對的操作識別，不以認購者相同推測有效，取消發送。
- `deliveryDiagnostics` 保存最近 200 筆未發送原因，包含批次／事件識別、用品 ID、驗證時間與原因碼。主要原因：`EVENT_CANCELLED`、`SPACE_UNAVAILABLE`、`ITEM_UNAVAILABLE`、`RESTOCK_RECORD_MISSING`、`UNVERIFIABLE_CLAIM_IDENTITY`、`CLAIM_OPERATION_REPLACED`、`CLAIM_NO_LONGER_PENDING`、`CLAIM_OWNER_CHANGED`、`MEMBERS_UNVERIFIABLE`、`NO_ELIGIBLE_RECIPIENTS`。
- 存檔版本不變；舊已發送通知不改寫。既有格式驗證不通過的批次仍沿用載入時錯誤紀錄，不強行投遞。

## 驗收與限制

測試涵蓋加入／退出、原本無接收者後加入、無接收者取消、認購取消再認購、接手被取代、部分失效、舊批次重整、無法查詢成員、通知保存失敗後重處理、補貨 Undo 及歷史通知不變。

localStorage 沒有跨裝置投遞或多分頁寫入鎖；來源為目前裝置的有效成員資料。若瀏覽器連來源用品資料都無法保存，無法保證關閉後仍記得該次操作；會記錄錯誤，不宣稱通知已建立。沒有新增背景或自動重試機制。
