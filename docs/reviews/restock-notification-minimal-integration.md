## 2026-10-18 規則調整：60 秒待發送與復原（待實作）

本節取代「補貨立即發布、Undo 不撤回」作為後續實作規則；不表示目前程式已完成延後發送。

### 發送與合併

- 共享空間補貨成功後先建立「待發送」事件，等待期間不進入成員可讀通知清單、不出現未讀提示，也不投遞給其他成員。
- 相同操作者、共享空間與操作類型，從第一筆成功操作起計算固定 60 秒。後續操作不重設截止時間；不同操作者、空間與類型分開計算。
- 待發送資料保存第一筆事件時間、截止時間、批次 ID、操作者、收件人，以及空間用品 ID／補貨紀錄 ID 與文字快照。相同事件不得重複入列或發送。
- 第 59 秒成功復原時，移除該次補貨事件；其他成員不收到該用品的補貨通知。多項批次只保留尚未復原的用品，全部復原則移除整批待發送通知。
- 依成功復原的實際結果更新待發送資料，不因使用者按了按鈕但復原失敗而取消有效事件。依紀錄 ID 判斷，不只看用品名稱、目前單位或「是否需要補貨」。
- 到達第一筆操作後 60 秒時，先確認相應補貨紀錄仍存在，再依仍有效的事件產生正式通知。背景分頁或關閉 App 可能使實際建立時間延後，但不可提早發送。
- 正式通知建立後，再進行的復原不撤回已發通知。截止邊界以已成功完成的操作及是否已正式建立通知為準。
- 補貨／推算立即執行，不等待通知；個人空間不建立共享待發送事件，操作者本人仍不收自己的共享通知。
- 本次規則不自動將 Toast 的 8 秒顯示時間延長為 60 秒；任何可用入口在截止前成功執行的 Undo 均適用。

### 安全交易順序

1. 先完成並確認單筆或整批補貨資料；批次失敗不入列。
2. 補貨成功後保存待發送事件；通知入列失敗保留可追查錯誤，不將成功補貨回報為失敗。
3. Undo 先按原本規則復原補貨，成功後取消相對應待發送事件，不覆寫後續單位週期或其他補貨。
4. 到期發送前重新檢查用品與紀錄 ID；待發送狀態、正式通知及已投遞事件識別在同一通知 Key 中一次保存，避免重整後重複發送。
5. 待發送事件必須持久化；重新開啟 App 後恢復截止時間、校驗補貨資料並處理到期事件，不重新開始 60 秒。
6. 通知保存失敗不可顯示為成功發送；不得因此新增、刪除或重複建立補貨紀錄。若未來加入跨裝置投遞，須在服務端落實同一等待及去重規則，不能宣稱目前 localStorage 已具備跨裝置通知。

### 必要驗收

- 第 0 秒補貨、第 59 秒 Undo、第 60 秒無該事件通知。
- 未復原事件在第 60 秒前不顯示，到期後只建立一次通知。
- 多項事件部分復原時只通知剩餘用品；全部復原則無通知。
- 固定 60 秒不因第 25、50 秒加入事件而延後；不同成員／空間／類型不混合。
- 重新整理前後保留原截止時間，已取消事件不重現、已發事件不重複。
- 通知存檔失敗、批次補貨失敗、單位變更後 Undo 均不破壞用品與歷史紀錄。
