# 補補｜Codex + SDD 開發守則（草案）

## 不可違反
1. 先讀取現有 `spec.md`、相關程式與 Figma 參考，再說明改動範圍。
2. 不得因規格整理而重寫或刪除已完成功能；沒有明確授權，不得修改與本次任務無關的檔案。
3. 如規格與程式不一致，列出衝突，不默默以其中之一覆蓋。
4. 先提出修改計畫與可能影響的檔案；執行後列出 `git diff` 摘要、測試結果及未完成項目。
5. 不自動 merge、push、刪除分支、改動其他組員工作；先檢查 `git status`。
6. 所有業務規則變動需同步修改 spec、決策日誌與程式（若本次授權實作）；按功能做小型 commit。
7. 使用目前 Vue + Vite + Pinia + Router + Sass；沒有必要不增加依賴或新的後端。
8. 資料範圍：不保證跨裝置共用，除非經正式後端決策及實作。

## AI 工具 / Skills
- 已知曾使用 Codex；目前專案實際模型、CLI 版本及啟用 Skills 名單尚未由本次 repo 證實，**不得編造**。
- 若啟用 Spec Kit，先用小型變更測試 `specify → clarify → plan → tasks → implement`。Codex 不應直接執行未核對的長串指令。
- Spec Kit 是流程工具，Git 是版本歷史來源；修改履歷應在 Git Commit 和 `DECISION_LOG.md` 保存。

## 每次開始任務的檢查清單
- 目前分支？有未提交改動嗎？
- 要解決的使用者問題及對應規格編號？
- 修改哪些檔案？不能修改哪些？
- 驗收條件及測試方式？
- 是否保留先前互動、資料及 RWD 行為？
