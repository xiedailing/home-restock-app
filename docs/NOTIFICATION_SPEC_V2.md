狀態：通知 V2 已於 feature/final-integration 本機整合，待組員驗收；完成狀態與限制見 NOTIFICATION_V2_HANDOFF.md。2026-10-18 已依使用者最新決定確認延後建立、鈴鐺查看狀態及全部已讀三項規則。

來源：使用者提供的 `/Users/mei/Downloads/bubu-notification-rules.html`。原始 HTML 完整保存在 [規格來源](sources/bubu-notification-rules-v2.html)，包含組員確認清單及版面示例。以下依原文件整理，後續口頭調整另外列出，不暗改原規則。

## 01｜通知入口與頁面

- 購買清單右上角頭貼替換為 `bell.svg`，維持尺寸、位置與 Soft UI 風格。
- 點擊鈴鐺進入獨立「通知」頁，不使用下拉面板。
- 通知按建立時間由新到舊；卡片顯示文字、日期及類型 icon。
- 鈴鐺有尚未查看的新通知時顯示小圓點，不顯示數字；查看與單筆已讀分開處理（見第 06 節）。
- 不做搜尋、分類篩選、手動刪除或全部清除。

## 02｜通知類型與對象

| 類型 | 觸發情境 | 接收者 |
| --- | --- | --- |
| 該補貨了 | 共享用品符合既有補貨提醒條件 | 依原提醒設定的相關成員 |
| 已認領 | 成員認領共享清單用品 | 同空間其他成員 |
| 已接手 | 接手其他成員認領的用品 | 同空間其他成員 |
| 已補貨 | 共享用品完成補貨 | 同空間其他成員 |

- 個人空間的購買操作不產生共享通知。
- 操作者不收到自己的操作通知。
- 取消認領不發送通知。
- 同一事件不得重複產生通知。

## 03｜通知文案規則

### 該補貨了

| 項數 | 完整範例 |
| --- | --- |
| 1 項 | 「家庭」的衛生紙該補貨了 |
| 2 項 | 「家庭」有 2 項用品該補貨：衛生紙、洗衣精 |
| 3 項 | 「家庭」有 3 項用品該補貨：衛生紙、洗衣精、垃圾袋 |
| 4 項以上 | 「家庭」有 5 項用品該補貨：衛生紙、洗衣精… |

### 已認領／已接手／已補貨

1～2 項列出用品名稱；3 項以上只顯示總數。

- 小明已認領「家庭」的衛生紙。
- 小明已認領「家庭」的衛生紙、酒精。
- 花花已接手「家庭」5 項用品。
- 小明已補貨「家庭」3 項用品。

通知文案使用事件發生時的成員、空間、用品資料。合併批次結束後，後續用品狀態改變不回寫歷史文字。

## 04｜固定 60 秒合併，結束後才正式建立通知

本節依 2026-10-18 最新決定，取代原 HTML「第一筆操作即建立通知」。認領、接手及已補貨全部適用；不自行將此等待規則套用到「該補貨了」提醒。

- 第一筆成功事件先持久化為待發送批次，固定截止時間為第一筆事件時間加 60 秒。
- 只有同一操作者、同一共享空間、同一操作類型，且在第一筆事件起 60 秒內的事件才能合併。
- 認領、接手、已補貨分別合併；不同操作者、空間、類型不得混合。
- 後續事件不延長計時；同一用品同批只計算一次；同一事件不得重複加入或發送。
- 60 秒結束後才正式產生一則通知。等待期間不顯示在通知列表、不亮新通知圓點，也不投遞給收件人。
- 操作資料立即更新，不等待通知；不修改補貨、單位週期、歷史與 Undo 的既有行為。
- 若 60 秒內認領全部取消，不產生通知；部分取消只保留剩餘用品。取消本身不產生新通知。
- 已補貨批次沿用先前確認的復原規則：第 59 秒成功復原該次補貨，移除相應事件；全部復原不發通知，部分復原只通知其餘用品。
- 待發送批次須保存固定 ID、事件 ID、第一筆時間、截止時間、操作者／空間／用品快照、收件人，以及對應用品 ID／補貨紀錄 ID。到期依相關操作是否仍有效判斷，不能由品名或目前是否待補貨猜測。
- 重新整理仍依已保存的批次及截止時間處理；不遺失、不重新起算，不重複產生通知。應於恢復後處理到期批次，不宣稱關閉 App 時有背景服務即時發送。
- 正式建立後歷史文字固定；之後取消或復原不撤回已正式建立的通知。
- 不將 Toast 的 8 秒自動改為 60 秒；任何既有可用入口在期限內成功執行的 Undo 均適用。

範例：10:00:00 衛生紙、10:00:25 洗衣精、10:00:50 垃圾袋，由小明在家庭認領；直到 10:01:00 才正式建立「小明已認領『家庭』3 項用品。」若 10:00:59 全部取消，則不建立通知。

原 HTML 的「已讀通知在合併期增加用品時暫採保留已讀」已不適用此三類操作：合併期尚無正式通知，使用者無從先讀取。到期後不得再向該通知合併事件。

**待確認：**恰好截止時間的事件／取消之先後順序，以及正式通知建立時間採實際發布或原事件時間。原事件時間及截止時間均須保留，不以重新整理時間覆蓋。

## 05｜取消認領

- 不產生新通知。
- 待發送批次 60 秒合併期內取消，移除對應用品；整批都取消則移除待發送批次，不產生正式通知。
- 合併期結束後取消，不修改舊通知。
- 點擊舊認領通知，進共享清單顯示最新認領狀態。

## 06｜卡片、查看與已讀狀態

### 卡片與單筆已讀

- 未讀：淺綠底、稍粗文字；已讀：白底、一般字重，不降低文字透明度。
- 卡片不顯示未讀圓點；鈴鐺只代表尚未查看的新通知。
- 點擊單筆通知標記該筆已讀；已讀項目仍可點擊。
- 進通知頁不自動將所有通知標記已讀。
- 已讀狀態依接收者分別保存，重新整理後保留。

### 鈴鐺查看狀態（seen）

- 新的正式通知產生時，對相應收件人標為尚未查看，鈴鐺出現圓點；待發送批次不計入。
- 使用者進入通知頁後，立即將目前列表通知標記為已查看，清除圓點。
- 已查看不等於已讀：只清除 seen 提示，不改變 read 或未讀卡片底色／字重。
- 之後再產生正式通知，圓點再次顯示。不得用一次性的全域「曾進過通知頁」旗標永久消除後續新通知提示。
- 每位接收者各自保存查看與已讀狀態，不能用某位成員的操作清除其他人的圓點。

### 全部已讀

- 保留通知頁標題右側的「全部已讀」按鈕，優先沿用現有淺綠 Soft UI 樣式。
- 點擊後，僅將目前通知列表內的所有通知標記已讀並持久化；不刪除通知、不跳轉，不處理尚未建立的待發送批次。
- 單筆點擊仍可標記已讀。
- 全部已讀或空列表時停用按鈕，沿用按鈕停用視覺；不新增另一套操作。

HTML 樣式示例包含「今天 10:30｜未讀」「昨天 18:20｜已讀」，是版面示例；正式日期格式未另外明訂。

**待確認：**沿用先前「當天 HH:mm、其他 MM/DD」的日期格式，以及左側各類型 Icon 的具體資源。不得只憑 HTML 示例新增相對日期格式。

## 07｜統一跳轉

| 類型 | 目的地 |
| --- | --- |
| 該補貨了／已補貨 | 我的用品 → 通知對應空間 |
| 已認領／已接手 | 購買清單 → 共享清單 → 通知對應空間 |

無論單項／多項，都不直接進用品詳情；顯示最新狀態。點舊通知不能重新認領、補貨或修改資料。

## 08｜舊通知與 Toast

補貨狀態變更不需要 Toast。全部待補貨、部分已補貨、全部已補貨、已補貨後再次待補貨，都正常跳轉。不顯示「此通知的用品皆已補貨」。通知記錄當時事件，列表顯示最新狀態。

| 特殊情況 | 跳轉 | Toast 原文 |
| --- | --- | --- |
| 部分用品已刪除 | 正常跳轉對應空間 | 此通知有部分用品已刪除 |
| 全部用品已刪除 | 留在通知頁 | 此通知的用品皆已刪除 |
| 空間不存在或無權限 | 留在通知頁 | 此空間已不存在或無法查看 |

刪除不等於已補貨。空間不可查看優先於用品刪除；一次點擊最多一則 Toast。無法跳轉的通知仍可標記已讀。

## 09｜空狀態

- 標題：「目前沒有通知」
- 說明：「有新的共享用品動態時，會顯示在這裡。」
- 不增加操作按鈕。

## 10｜資料保留

- 最近 6 個月，已讀／未讀皆適用；過期自動移除。
- 不影響用品、購買清單、補貨與認領紀錄。
- 重整後保留未過期通知及已讀狀態。
- 可在 App 啟動或開通知頁時清理。

## 11｜開發範圍與限制

- 沿用 Vue 3、Vue Router、Pinia、localStorage、Sass 與 Soft UI。
- 通知包含 ID、類型、事件時間、操作者、接收者、空間 ID、用品 IDs、已讀狀態、合併視窗起點。
- 同批不重複計數；查看及已讀狀態依接收者分別保存。
- 沒有後端／跨裝置即時同步；localStorage 只在各自瀏覽器儲存環境生效。
- 不重做購買清單／我的用品，不讓通知影響補貨資料。
- **待確認：**無完整登入成員 ID 時的本機成員切換／驗收方式；不得把展示通知當成跨成員投遞已完成。
- **待確認：**舊正式通知沒有用品 IDs／接收者已讀表時的相容遷移；不可由文案猜測歷史用品。
- **待確認：**「該補貨了」的穩定事件鍵與再次提醒時機，需沿用提醒設定並避免每次開頁重複通知，不更動提醒公式。

## 資料結構檢查：現況與必要擴充（設計，未實作）

檢查對象：`feature/final-integration/src/stores/sharedNotifications.js`。目前為最小補貨通知 Store，只有 `records`，`publishMemberEvent()` 立即 push 已補貨通知。沒有待發送批次、截止時間、事件去重表或正式查看／已讀 API。舊 WIP 有單一 `read/seen` 與 `markAllSeen()`，但未依收件人區分，也未具備 60 秒批次。

| 資料 | 建議欄位／責任 | 相容與保護 |
| --- | --- | --- |
| 待發送批次 | `pendingBatches[]`：固定 `id`、`actorId`、`spaceId`、`type`、`firstEventAt`、`deadlineAt`、`recipientIds`、事件與用品名稱快照 | 第一筆即保存，後續不改 deadline；不混入可見 records |
| 批次事件 | `events[]`：穩定 `eventId`、`itemId`、事件時間／名稱快照；補貨另含 `recordId` | 用品按 ID 計數、事件按 ID 去重；取消／Undo 只刪對應成功操作，不修改用品本體 |
| 正式通知 | 保留現有 `id/type/source/message/createdAt/recipientIds`，增加 `batchId`、事件 IDs、用品 IDs／快照與原事件時間 | 可以由 batchId 決定穩定通知 ID；到期保存 records 與移除 pending 必須同一次通知 Key 寫入 |
| 收件人狀態 | 例如 `recipientState[memberId] = { seen: false, read: false }` | 進頁僅改 seen；點單筆／全部已讀改 read；不得跨收件人改狀態 |
| 發布去重 | 已完成批次／事件識別，或可驗證等效方案 | 重整、重複排程或取消後再操作，不得重複建立通知；取消後再認領須是新操作事件 |

上表是最小資料責任建議，不是宣稱 API 已存在。正式欄位命名與排程 API 在程式階段定案。

### 持久化與重整

- 沿用 `STORE_KEYS.sharedNotifications`；目前 Key 已存在，不需修改 `STORAGE_VERSION`、Catalog journal 或單位 Store。
- 舊存檔沒有 pending 欄位時視為空陣列，不能將既有正式通知重新排入等待。
- 保留未知存檔欄位、合法舊通知、原文及建立時間；不因缺 IDs／新狀態表而刪除歷史或重建 demo。
- 舊單筆 read／seen 如何映射多收件人資料仍待程式階段確定，不能把一人的已讀直接當所有人已讀。
- 先建下一份通知狀態，確認同一通知 Key 寫入成功後才套用記憶體；發布失敗不能先亮圓點或先清除 pending。
- 不以跨 Key 完整交易保證作宣稱；補貨成功／Undo 成功與通知入列／取消之間的故障，需保存可追查錯誤，發布前再以用品／紀錄 ID 校驗，不能為通知重做補貨。
- 啟動／回到前景恢復已保存批次，依原 deadline 排程；到期先處理固定視窗，不因新事件到來延長。清理計時器避免重複回呼。
