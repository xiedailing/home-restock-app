## 01｜通知入口與頁面

- 購買清單右上角頭貼替換為 `bell.svg`，維持尺寸、位置與 Soft UI 風格。
- 點擊鈴鐺進入獨立「通知」頁，不使用下拉面板。
- 通知按建立時間由新到舊；卡片顯示文字、日期及類型 icon。
- 鈴鐺有尚未查看的新通知時顯示小圓點，不顯示數字；查看與單筆已讀分開處理（見第 06 節）。
- 不做搜尋、分類篩選、手動刪除或全部清除。

## 02｜通知類型與對象

| 類型 | 觸發情境 | 接收者 |
| --- | --- | --- |
| 該補貨了 | 個人或共享空間用品符合補貨提醒條件 | 個人空間僅本人；共享空間依各成員提醒設定通知符合資格者 |
| 已認領 | 成員認領共享清單用品 | 同空間其他成員 |
| 已接手 | 接手其他成員認領的用品 | 同空間其他成員 |
| 已補貨 | 共享用品完成補貨 | 同空間其他成員 |

- 「該補貨了」適用於個人與共享空間。個人空間僅通知本人；共享空間依各成員提醒設定及有效資格決定接收者，不得只因身為空間成員就一律通知。
- 已認領、已接手、已補貨為共享操作通知，不適用於個人空間。
- 操作者不收到自己的共享操作通知；此排除不適用於本人接收的「該補貨了」提醒。
- 取消認領不發送通知。
- 同一事件不得重複產生通知。

### 2026-10-19 提醒對象更正與實作差距

上述個人／共享空間適用範圍以使用者最新決定為準。「該補貨了」與共享操作通知必須分開判斷，不能共用「只限共享空間」或「排除操作者」的限制。

目前工作分支已補齊個人空間的 `restock-due` 本人提醒、去重、個人延後篩選與點擊跳轉；共享操作通知仍只限共享空間。尚未具備其他成員各自的完整提醒偏好資料，共享空間依各成員設定篩選的部分仍待整合，不得宣稱僅憑成員名單已完成資格判斷。

## 03｜通知文案規則

### 該補貨了

| 項數 | 完整範例 |
| --- | --- |
| 1 項 | 「家庭」的衛生紙該補貨了 |
| 2 項 | 「家庭」有 2 項用品該補貨：衛生紙、洗衣精 |
| 3 項 | 「家庭」有 3 項用品該補貨：衛生紙、洗衣精、垃圾袋 |
| 4 項以上 | 「家庭」有 5 項用品該補貨：衛生紙、洗衣精… |

### 已認領／已接手／已補貨

1～2 項列出用品名稱；3 項以上只顯示總數。

- 小明已認領「家庭」的衛生紙。
- 小明已認領「家庭」的衛生紙、酒精。
- 花花已接手「家庭」5 項用品。
- 小明已補貨「家庭」3 項用品。

通知文案使用事件發生時的成員、空間、用品資料。合併批次結束後，後續用品狀態改變不回寫歷史文字。

## 04｜固定 60 秒合併，結束後才正式建立通知

本節依 2026-10-18 最新決定，取代原 HTML「第一筆操作即建立通知」。認領、接手及已補貨全部適用；不自行將此等待規則套用到「該補貨了」提醒。

- 第一筆成功事件先持久化為待發送批次，固定截止時間為第一筆事件時間加 60 秒。
- 只有同一操作者、同一共享空間、同一操作類型，且在第一筆事件起 60 秒內的事件才能合併。
- 認領、接手、已補貨分別合併；不同操作者、空間、類型不得混合。
- 後續事件不延長計時；同一用品同批只計算一次；同一事件不得重複加入或發送。
- 60 秒結束後才正式產生一則通知。等待期間不顯示在通知列表、不亮新通知圓點，也不投遞給收件人。
- 操作資料立即更新，不等待通知；不修改補貨、單位週期、歷史與 Undo 的既有行為。
- 若 60 秒內認領全部取消，不產生通知；部分取消只保留剩餘用品。取消本身不產生新通知。
- 已補貨批次沿用先前確認的復原規則：第 59 秒成功復原該次補貨，移除相應事件；全部復原不發通知，部分復原只通知其餘用品。
- 待發送批次須保存固定 ID、事件 ID、第一筆時間、截止時間、操作者／空間／用品快照、收件人，以及對應用品 ID／補貨紀錄 ID。到期依相關操作是否仍有效判斷，不能由品名或目前是否待補貨猜測。
- 重新整理仍依已保存的批次及截止時間處理；不遺失、不重新起算，不重複產生通知。應於恢復後處理到期批次，不宣稱關閉 App 時有背景服務即時發送。
- 正式建立後歷史文字固定；之後取消或復原不撤回已正式建立的通知。
- 不將 Toast 的 8 秒自動改為 60 秒；任何既有可用入口在期限內成功執行的 Undo 均適用。

範例：10:00:00 衛生紙、10:00:25 洗衣精、10:00:50 垃圾袋，由小明在家庭認領；直到 10:01:00 才正式建立「小明已認領『家庭』3 項用品。」若 10:00:59 全部取消，則不建立通知。

原 HTML 的「已讀通知在合併期增加用品時暫採保留已讀」已不適用此三類操作：合併期尚無正式通知，使用者無從先讀取。到期後不得再向該通知合併事件。

**待確認：**恰好截止時間的事件／取消之先後順序，以及正式通知建立時間採實際發布或原事件時間。原事件時間及截止時間均須保留，不以重新整理時間覆蓋。

## 05｜取消認領

- 不產生新通知。
- 待發送批次 60 秒合併期內取消，移除對應用品；整批都取消則移除待發送批次，不產生正式通知。
- 合併期結束後取消，不修改舊通知。
- 點擊舊認領通知，進共享清單顯示最新認領狀態。

## 06｜卡片、查看與已讀狀態

### 卡片與單筆已讀

- 未讀：淺綠底、稍粗文字；已讀：白底、一般字重，不降低文字透明度。
- 卡片不顯示未讀圓點；鈴鐺只代表尚未查看的新通知。
- 點擊單筆通知標記該筆已讀；已讀項目仍可點擊。
- 進通知頁不自動將所有通知標記已讀。
- 已讀狀態依接收者分別保存，重新整理後保留。

### 鈴鐺查看狀態（seen）

- 新的正式通知產生時，對相應收件人標為尚未查看，鈴鐺出現圓點；待發送批次不計入。
- 使用者進入通知頁後，立即將目前列表通知標記為已查看，清除圓點。
- 已查看不等於已讀：只清除 seen 提示，不改變 read 或未讀卡片底色／字重。
- 之後再產生正式通知，圓點再次顯示。不得用一次性的全域「曾進過通知頁」旗標永久消除後續新通知提示。
- 每位接收者各自保存查看與已讀狀態，不能用某位成員的操作清除其他人的圓點。

### 全部已讀

- 保留通知頁標題右側的「全部已讀」按鈕，優先沿用現有淺綠 Soft UI 樣式。
- 點擊後，僅將目前通知列表內的所有通知標記已讀並持久化；不刪除通知、不跳轉，不處理尚未建立的待發送批次。
- 單筆點擊仍可標記已讀。
- 全部已讀或空列表時停用按鈕，沿用按鈕停用視覺；不新增另一套操作。

HTML 樣式示例包含「今天 10:30｜未讀」「昨天 18:20｜已讀」，是版面示例；正式日期格式未另外明訂。

**待確認：**沿用先前「當天 HH:mm、其他 MM/DD」的日期格式，以及左側各類型 Icon 的具體資源。不得只憑 HTML 示例新增相對日期格式。

## 07｜統一跳轉

| 類型 | 目的地 |
| --- | --- |
| 該補貨了／已補貨 | 我的用品 → 通知對應空間 |
| 已認領／已接手 | 購買清單 → 共享清單 → 通知對應空間 |

無論單項／多項，都不直接進用品詳情；顯示最新狀態。點舊通知不能重新認領、補貨或修改資料。

## 08｜舊通知與 Toast

補貨狀態變更不需要 Toast。全部待補貨、部分已補貨、全部已補貨、已補貨後再次待補貨，都正常跳轉。不顯示「此通知的用品皆已補貨」。通知記錄當時事件，列表顯示最新狀態。

| 特殊情況 | 跳轉 | Toast 原文 |
| --- | --- | --- |
| 部分用品已刪除 | 正常跳轉對應空間 | 此通知有部分用品已刪除 |
| 全部用品已刪除 | 留在通知頁 | 此通知的用品皆已刪除 |
| 空間不存在或無權限 | 留在通知頁 | 此空間已不存在或無法查看 |

刪除不等於已補貨。空間不可查看優先於用品刪除；一次點擊最多一則 Toast。無法跳轉的通知仍可標記已讀。

## 09｜空狀態

- 標題：「目前沒有通知」
- 說明：「有新的共享用品動態時，會顯示在這裡。」
- 不增加操作按鈕。

## 10｜資料保留

- 最近 6 個月，已讀／未讀皆適用；過期自動移除。
- 不影響用品、購買清單、補貨與認領紀錄。
- 重整後保留未過期通知及已讀狀態。
- 可在 App 啟動或開通知頁時清理。

## 2026-10-19 最新決定：購買清單個人延後提醒

來源：使用者於 2026-10-19 確認的九項規則，以及「站內通知即可，目前沒有真的開發到這功能」。本節新增購買清單提醒需求，對此前「不新增提醒類型或計時規則」的限制構成此功能範圍內的例外；既有認領、接手與補貨的固定 60 秒批次規則不變。

### 操作與影響範圍

1. 點擊用品卡片的「延後提醒」，開啟日期選擇視窗。手機採 Sheet，桌面沿用右側面板。
2. 選擇日期並確認後，按鈕顯示「延至 10/20」等月／日文字。
3. 再次點擊，可查看目前日期、修改或取消延後提醒。
4. 到達設定日期時，按鈕恢復「延後提醒」。按鈕文字恢復與當日 08:00 通知觸發是兩個時點，不可因恢復文字而遺失待提醒事件。
5. 延後僅作用於該用品、該操作者，不更動全域提醒設定，也不影響其他共享成員。
6. 視窗說明：「僅延後你對此用品的提醒，其他成員不受影響。」
   - 視窗僅保留標題「延後提醒」、上述說明、日期選擇（例如「10/20 週二」）及「儲存／取消延後」按鈕。不另顯示「選擇下次提醒日期」或「目前延後至」文字；只有已儲存且仍有效的延後設定才顯示「取消延後」；尚未設定或已失效時隱藏，不保留停用按鈕。桌面沿用共用返回鍵。
7. 延後期間可再次修改或取消日期；舊排程不得因修改、取消後繼續誤發。
8. 點擊「取消延後」並成功儲存後，移除該用品、該操作者已建立的延後日期，按鈕恢復「延後提醒」。原延後日期的提醒失效，不再套用；該用品僅依一般「未購買提醒」規則處理，不更改全域提醒天數，也不影響其他成員。取消操作本身不立即建立一則提醒；後續是否提醒由一般規則判斷。存檔失敗時保留原延後設定並顯示錯誤。

目前日期選擇器限制最早明天；是否允許當日 08:00 前設定當日提醒，使用者尚未決定，不自行放寬。

### 到期與站內通知

- 延後日期當天早上 **08:00** 觸發一次站內提醒；目前不要求系統通知權限、Service Worker 或背景推播服務。
- 同一有效延後事件到期後只建立一次提醒；重新整理、重新開頁或重試不得重複建立。
- 發送前確認用品仍存在、仍在待買清單、尚未補貨，接收者仍有權查看該空間；用品已補貨或已移除，不再提醒。
- 延後期間，該接收者的該用品不參與一般未購買提醒；其他成員依自己的設定處理。
- 通知保存失敗不得標記為已發送，通知失敗不得中斷用品操作。
- 不將目前 localStorage 站內展示宣稱為關閉網頁後仍能準時發送的真正推播。

### 與一般未購買提醒合併

- 相同空間、相同接收者、相同觸發時間的「一般未購買提醒」與「延後提醒」，合併為一則站內通知。
- 延後提醒優先於一般未購買提醒；以用品 ID 去重，同一用品不得重複計數或重複列名。
- 不同空間、不同接收者或不同觸發時間不得混合。
- 此規則不沿用認領／接手／已補貨通知的 60 秒合併視窗。

### 尚待確認

- 08:00 使用台灣時間（Asia/Taipei）或裝置當地時間。
- App 關閉、休眠或離線而錯過 08:00 時，下次開啟是否補發，以及補發期限。
- 一般未購買提醒的實際觸發時間、重複頻率；「相同時間」使用相同排程時刻或其他時間粒度。
- 合併提醒的正式文案、通知類型與點擊跳轉目的地。不得自行套用「該補貨了」的預測補貨語意。
- 關閉提醒偏好時，是否仍保留或建立這類站內通知。
